# Question-Scoped HotpotQA Passage Pipeline

## Goal

Materialize the `context` values already stored in `hotpot_qa` into a deduplicated passage corpus while preserving each question's ten allowed retrieval candidates. The resulting data must support idempotent rebuilds and question-scoped retrieval without exposing `supporting_facts` to the agent.

## Scope

### In scope

- Add a canonical `SourcePassage` table for one stored HotpotQA context paragraph.
- Add a `HotpotQAContext` association table linking each QA row to its context passages and original positions.
- Normalize passage identity and compute a content hash for exact deduplication after normalization.
- Materialize passages and links from existing `hotpot_qa` rows in resumable database batches.
- Preserve the original ordered sentence list for supporting-fact evaluation.
- Add migration and unit tests for identity, extraction, deduplication, and idempotent relationships.

### Out of scope

- Embedding generation and vector-index creation.
- Semantic or fuzzy near-duplicate detection.
- Retrieval API and answer-generation behavior.
- Replacing the raw `hotpot_qa` records.
- Using `supporting_facts` as input to materialization or retrieval.

## Current context

`backend/src/backend/scripts/ingestion.py` streams the Hugging Face `hotpotqa/hotpot_qa` distractor configuration into `hotpot_qa`. Hugging Face represents `context` as parallel `title` and `sentences` arrays; each paired value is one paragraph. The raw QA table remains the source of truth for evaluation.

The working tree already contains an incomplete UUIDv7 `SourceDocument` model. It will be replaced by the more precise `SourcePassage` model because the stored unit is a paragraph, not a full article.

## Data model

### `source_passage`

- `id`: UUIDv7 primary key generated by the application.
- `title`: original title for display and evaluation.
- `normalized_title`: NFKC-normalized, whitespace-collapsed, case-folded title used for identity.
- `sentences`: JSONB array preserving the original sentence order and text.
- `text`: normalized sentence text joined with a single space for embedding and retrieval input.
- `content_hash`: SHA-256 of the normalized sentence text.
- Unique constraint on `(normalized_title, content_hash)`.

The UUID is a row identity only. The composite natural key performs deduplication and makes reruns safe.

### `hotpot_qa_context`

- `hotpot_qa_id`: foreign key to `hotpot_qa.id`.
- `source_passage_id`: foreign key to `source_passage.id`.
- `position`: zero-based position from the original context array.
- Composite primary key `(hotpot_qa_id, position)` so every original context position is preserved.
- Index `(hotpot_qa_id, source_passage_id)` for the retrieval join.

The association is the retrieval boundary: a query for a QA row may only search passages linked through this table. `supporting_facts` remains evaluation metadata and is not copied into either corpus table.

## Normalization and identity

For each title and sentence:

1. Apply Unicode NFKC normalization.
2. Remove soft hyphens.
3. Collapse runs of whitespace and strip the result.
4. Join normalized sentences with one space for `text`.
5. Case-fold the normalized title for `normalized_title`.
6. Hash the UTF-8 `text` with SHA-256.

The ordered sentence list is retained separately, so sentence indices in `supporting_facts` remain meaningful. Two passages with the same title but different sentence content remain separate records. No fuzzy threshold is used in this first version.

## Materialization flow

The raw HF ingestion remains unchanged in responsibility. A separate `build_passages` command reads persisted `hotpot_qa` rows in primary-key batches:

1. Flatten each row's paired `context.title` and `context.sentences` arrays.
2. Validate that the arrays have matching lengths; reject malformed rows with a clear error.
3. Normalize and hash each passage.
4. Insert unseen `source_passage` keys with `ON CONFLICT DO NOTHING`.
5. Resolve IDs for all keys in the batch.
6. Insert `(hotpot_qa_id, source_passage_id, position)` links with `ON CONFLICT DO NOTHING`.
7. Commit the batch and continue from the next QA primary-key batch.

The command is safe to rerun. It does not delete rows, rewrite existing passage text, or create duplicate associations. It should report rows scanned, candidate passages, newly inserted passages, and newly inserted links.

## Retrieval contract

Embedding is a later stage. When it is added, embeddings belong to `SourcePassage` (or a versioned embedding table), while retrieval must join/filter through `HotpotQAContext` for the requested QA ID. The agent receives retrieved passage title and text only. Evaluation can join back to the raw QA row and compare retrieved passage titles and sentence spans with `supporting_facts`.

## Error handling and invariants

- Missing `context`, missing `title`, missing `sentences`, or mismatched parallel-array lengths fail the affected batch before commit.
- Empty normalized text is rejected rather than indexed.
- A failed batch can be rerun without manual cleanup.
- Foreign keys prevent orphaned associations.
- Unique constraints enforce both passage identity and original per-question position.

## Verification

Unit tests must prove:

- normalization is deterministic and removes only the specified formatting variation;
- extraction pairs titles and sentence lists by position;
- the same normalized `(title, text)` yields one passage identity;
- the same title with different text yields two passage identities;
- sentence order is preserved;
- malformed context arrays are rejected;
- rerunning materialization is idempotent at the passage and association levels.

The migration must apply cleanly to the current schema, and the existing raw ingestion behavior must continue to pass its validation checks.
